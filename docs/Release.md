# How releases are published

Releases are cut by the `Auto-release` GitHub workflow (`.github/workflows/zz_generated.auto_release.yaml`, generated by [devctl](https://github.com/giantswarm/devctl)) from [conventional commit](https://www.conventionalcommits.org/) subjects. Pull requests are squash-merged, so the PR title is the commit subject; the `semantic-pull-request` check validates it.

## Release candidates

Every merge to `main` that carries a releasable change creates the next `vX.Y.Z-rc.N` tag and a GitHub pre-release with notes generated by [git-cliff](https://git-cliff.org/) (`cliff.toml`):

- `feat:` bumps the minor version, `feat!:` or a `BREAKING CHANGE` footer the major version, every other releasable type (`fix:`, `chore:`, `ci:`, `build:`, `refactor:`, `perf:`, `security:`) the patch version.
- `docs:`, `test:` and `style:` commits, and subjects that are not conventional, release nothing.

The tag triggers the CircleCI pipeline, which builds the binaries for every platform, attaches them and the krew archives to the release, and pushes the container image.

## Stable releases

A stable `vX.Y.Z` promotes the latest release candidate: run the `Auto-release` workflow by hand with `release-type: stable` ([Actions](https://github.com/giantswarm/kubectl-gs/actions/workflows/zz_generated.auto_release.yaml) → *Run workflow*). The stable tag lands on the candidate's commit, so what ships is what was tested.

The stable tag's CircleCI pipeline also runs `update-krew-index`, which opens the pull request to the [krew-index](https://github.com/kubernetes-sigs/krew-index) repository. Release candidates never reach krew.

## Changelog

`CHANGELOG.md` keeps the user-facing changes under `## [Unreleased]`; the GitHub release notes are generated from the commit subjects.
